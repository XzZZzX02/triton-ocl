# Two-column register tiling: accepted wave64 iteration

Accepted on 2026-11-06 after continuing the interrupted 2026-11-02 study.
This iteration adds the cache-keyed `matmul_register_tiling_2col` option,
default `False`, to the existing register-tiling pass, together with the
mandatory late `sycl-two-column-launch-guard` pass. It is a bounded gfx906
scalar/vector optimization. It introduces no MFMA, fast math or reassociation.
The broader all-model/backend optimization objective is not complete.

## Applicability and pipeline contract

The existing four-column decisions are unchanged. Two columns are considered
only when four-column tiling leaves fewer than 64 independent distributed
output points and two-column tiling leaves at least 64. The existing normalized
static-loop, owned/distinct buffer, indexing and two-f16-input/f32-accumulator
proofs remain required. The row extent is at least eight, the column extent at
least 16 and divisible by four, and K at least 16. Two-column candidates further
require static identity-layout scratch buffers and a public, void, uncalled
kernel entry. Batch loops within the same distributed nest count toward
parallelism; separate Triton grid programs do not.

The register lanes process columns separated by N/2, so neighboring work-items
still access adjacent columns. The affine and already-promoted SCF paths keep
each output's original K recurrence. Decisions inspect IR and available work;
they do not match model/kernel names or a list of benchmark dimensions.
Power-of-two frontend tiles are device-tested. Additional non-power-of-two
internal domains have structural coverage, not a claimed device speedup.

After initializer forwarding, ordered unroll and storage planning, the launch
guard proves the two SSA recurrences are isomorphic under column/carry
substitution. It derives the untiled branch from the first recurrence, restores
the column domain and drops dead second-lane operations, including potentially
out-of-bounds initial loads. The exact initial constant and ordered arithmetic
are preserved. A subsequent ordered-unroll invocation restores the original
untiled K=16 opportunity. An untiled-path marker prevents re-tiling on repeated
pass invocations. Asymmetric recurrences, effects and stale distribution/tile
markers fail closed with diagnostics.

The pass chooses tiling only when the actual product of the three local-range
dimensions is **exactly 64**. The renderer validates this recorded predicate
and lowers it mechanically to host dispatch between two C++ template
instantiations. Device selection is `if constexpr`, so the tiled alternative
cannot change fallback register allocation through a shared device branch.
The same dispatch is present in normal and profiling wrappers. This is not an
emitter-side scheduling heuristic. Unsupported/malformed predicates and calls
to specialized entries are rejected with clean translator exit code 1.

## Accepted evidence and provenance

`sycl-validation/two-column/wave64-analysis.json` is generated by
`audit_two_column_wave64.py`. It verifies expected configuration keys, complete
Slurm states, gfx906 logs, positive raw event samples, medians, generated-source
hashes, frozen input manifests, source preservation and fallback LLVM evidence.
With `--repo`, it also requires production files to match the measured sources.
No production code changed after the measured build:

- `libtriton.so`: `112f2e13787ace13e87235fb75683eec0c69db25435570073e1525a49387497f`
- `triton-sycl-translate`: `4ee80564c5d9cbd2a6439b261176fb194f79354d7c54420f4bf8fc81a9e0caf4`

The accepted archive consists of `wave64-matrix/` (34 device jobs) and
`wave64-extended/` (three additional ablation/launch jobs plus CPU and compile
cost checks). Every device job completed with exit 0 on an allocated Slurm
node and recorded gfx906. GPU kernels were not run on the login node.

- 2,555 structural checks: 123 two-column, 480 boundary/order/idempotence,
  218 launch-guard, 33 template contracts and 1,701 existing pass regressions.
  The 33 template contracts were repeated with an assertion that each of the
  four invalid-input cases exits 1; the tested harness is separately frozen.
- Four NN/NT/TN/TT frontend compile matrices, 20 configurations each; 44 layout
  compile cases; and 15 historical disabled/inert sources replayed byte-identically.
- 902 device runtime configuration records: 504 launch records, 134 dot
  records and 264 schedule/round records across 44 model-style layout cases.
  Of these, 870 are timed, producing 26,970 raw device-event samples and
  797,428 exact output/padding comparisons.
- CPU OpenMP: eight complete records at eight local ranges per record,
  totaling 25,024 bitwise/classified comparisons. CPU timings are not GPU gains.
- 36 separate cold-cache Triton-to-SYCL compilations. Imports, native C++
  compilation and execution are excluded. Context medians are 0.752–0.794 s;
  enabled/baseline median ratios range from 0.968 to 1.036. The largest measured
  increase is about 3.65% for full-stack K=16. C++/device JIT compilation cost,
  host dispatch latency and end-to-end application latency are not measured.

Launch coverage includes local sizes 1, 3, 15 `(3,5)`, 48, 64, 128 and 256,
including 3D local ranges `(4,4,4)` and `(4,4,8)`. Dot cases cover K=16/32/64/
128/256, full/tail/empty/unit masks, rounded random fp16 inputs, half subnormals
and extrema, infinities, NaNs and signed zeros. References round every product
and addition to f32 in order and include masked-zero K iterations. The 44
layouts include NN/NT/TN/TT, padding/strides, reversed axes, row/column broadcast
and grid-batched/batch-broadcast tensors. They are representative layouts, not
all external models or all physical rank-three contraction nests.

## Performance and actual pass interactions

Timings use ten warmups, 31 event samples per configuration, three rounds and
alternating configuration order. Event durations exclude host dispatch,
compilation and transfers. Output/padding is checked after profiling.
Speedup below is baseline median / enabled median, using each configuration's
three round medians. Every one of the 177 paired rounds in the 59 active
contexts improves; no performance tolerance is used to accept an active loss.

| Active context | Count | Median speedup range |
| --- | ---: | ---: |
| fp16 representative layouts, local=64 | 22 | 1.0284–1.0541x |
| Dot lengths and stack ablations, local=64 | 15 | 1.0224–1.1416x |
| Launch studies at local-product=64, including `(4,4,4)` | 22 | 1.0225–1.1447x |

Full-stack held-out K=64/128/256 dot results are 1.1168/1.1224/1.1301x.
The minimum individual paired-round ratio across active contexts is 1.02196x.
These are measurements of this recognized class on gfx906, not a universal
cost-model theorem.

Staging, initializer forwarding and ordered unroll actually coexist with
tiling. The harness verifies retained stage/store decisions, branch-local
forwarding and the expected short-tiled-unroll exception. K=16 retains unroll
in the fallback; K>=32 can unroll both alternatives. Register promotion is
subsumed by tiling's private accumulators. With the independent promotion
option off, tiling can enable initializer forwarding and SSA optimization;
this is an enabling interaction, not two multiplicative independent gains.

Reuse, fusion, group reduction and terminal-store requests do not all match
these particular dot kernels. Some reuse storage plans have identical before/
after sizes. Their ablations are controls, not proof of active independent
speedups. The archive checks 76 inert paired-source equalities, including f32,
no-distribution, tiling-off and existing four-column controls. Independence is
supported only for the tested active interactions; arbitrary pass orders and
all models are not claimed to be mutually unaffected.

## Fallback preservation, including small timing losses

There are 62 non-wave64 launch contexts. The archive contains 59 actual LLVM
pairs: three no-fusion contexts reused the same job's no-reuse dumps only after
both generated SYCL source hashes and the physical local size matched. Those
kernels share the JIT cache. Missing dumps are not counted as new measurements.

`compare_two_column_llvm.py` compares the final AdaptiveCpp LLVM modules after
bijective renaming of the entry, local SSA/block identifiers, attribute groups
and metadata graph IDs. It retains instructions, flags, operands, types,
address spaces, alignments, attributes and transitive alias/TBAA/loop metadata,
including graph sharing and self-cycles. It excludes source filenames/comments
and explicitly records only the additional null/undef dimension annotations
for kernels absent from the final module. It does not strip all metadata or
claim a general semantic-equivalence solver. Its own tests ensure arithmetic,
fast-math, alignment, attribute and metadata changes remain visible.

56 of the 59 LLVM pairs match under that bounded comparison. These account for
59 launch contexts after identical-source dump reuse. Their measured context
ratios span 0.99340–1.00459x; individual rounds span 0.97188–1.01093x. Small
below-baseline readings remain in the audit. Code equality is the preservation
evidence here, not a claim that every observed timing exceeds one.

The remaining three LLVM pairs are the no-accumulator ablation at local=48/
128/256. They differ because tiling-derived fallback retains SSA promotion.
Every paired round improves, with median ratios 1.06665/1.03306/1.03737x.
These are reported as measured enabling effects, not identical fallback code.
No arbitrary percentage tolerance was introduced to hide a changed slow path.

## Rejected studies retained separately

- `first-matrix/` retains the failed early marker assertion and partial records.
  The harness had incorrectly treated newly enabled initializer forwarding as
  a lost optimization. Partial results are not included in acceptance totals.
- `final-matrix/` is the historical unguarded local=64 study. Its PASS does not
  accept the later physical-launch cost rule.
- `launch-matrix/` shows repeatable unguarded local=128/256 regressions, up to
  about 27.6% slower. Its historical audit intentionally fails acceptance.
- `device-guard-matrix/` records the first device-branch repair. Separate host
  templates remove shared device scheduling/register allocation concerns.
- `template-pilot/` tests the earlier `<=64` rule. Its local=48 regression is
  why the accepted rule is `==64`, rather than all partial-wave launches.

Historical manifests and source snapshots are immutable. The extended launch
runner adds `--plans`; its own manifest records that test-only change. The
clean-exit assertion is likewise frozen separately. Neither change alters the
production compiler measured by all 37 jobs.

## Reproduction

In the configured DFCS build, execute device tests only inside an allocated
Slurm node (`ACPP_VISIBILITY_MASK=hip`). CPU semantic checks use `omp` instead.
For example, from the repository root:

```sh
python-triton python/test/sycl/two_column_contracts.py --output contracts.json
python-triton python/test/sycl/two_column_extended_contracts.py --output extended.json
python-triton python/test/sycl/two_column_guard_contracts.py --output guard.json
python-triton python/test/sycl/two_column_template_contracts.py --output templates.json
python-triton python/test/sycl/two_column_semantics.py --layout TT --rounds 3 --repeats 31 --output dot.json
python-triton python/test/sycl/two_column_launch_performance.py --layout TT --k 32 --blocks 48 64 128 256 --rounds 3 --repeats 31 --capture-codegen --dump-dir sources --output launch.json
python-triton python/test/sycl/model_layout_semantics.py --all --schedule two-column-pair --rounds 3 --repeats 31 --python /path/to/python-triton --output layouts.json
```

Read-only acceptance audit, requiring no GPU or Triton installation:

```sh
python3 -m unittest discover -s python/test/sycl -p test_compare_two_column_llvm.py
python3 python/test/sycl/audit_two_column_wave64.py docs/backend/sycl-validation/two-column --repo . --output /tmp/wave64-analysis.json
```

Primary compiler/paper sources and the next, unimplemented LDS bank-conflict
candidate are recorded in `sycl-optimization-research.md`. New independent
optimization work should start after committing this accepted iteration.
